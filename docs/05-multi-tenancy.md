# 05 · Multi-tenancy

**Hard requirement:** Organization A must never access Organization B's data.

**Hierarchy:** `Platform → Organization (tenant) → Brand → Branch → Zone → Device`.

**Strategy:** a shared database with a shared schema and an `organizationId` on every tenant row. This scales to thousands of small tenants cheaply and keeps cross-tenant platform analytics simple. Isolation is enforced by **three independent layers**, so a bug in any one of them can't leak data.

## Layer 1 — Referential: composite tenant foreign keys

Every tenant table declares `@@unique([id, organizationId])`. Children reference parents with **composite** FKs:

```prisma
branch Branch @relation(fields: [branchId, organizationId], references: [id, organizationId])
```

Postgres FK checks **bypass RLS**. With single-column FKs, a row in org A could legally point at `branchId` from org B. Composite keys make that physically impossible.
- `test/tenancy.static.test.ts` fails CI if any tenant → tenant relation isn't composite.
- It has already caught and fixed two gaps: `WalletTransaction.reverses` and `PromotionRedemption.promoCode`.

## Layer 2 — Application: scoped Prisma client

`packages/db/src/client.ts` exposes one entry point for tenant data:

```ts
await db.withTenant(ctx, async (tx) => {
  return tx.device.findMany({ where: { status: "AVAILABLE" } });
});
```

- **Where `ctx` comes from:** it's built from a verified credential: the JWT subject's employee record, the device certificate, or the API key. It's never taken from a header or body field.
- **What the Prisma extension does** (`tenant-scope.ts`) to every query on a tenant model:
  - merges `organizationId = ctx.organizationId` into `where` (reads, updates, deletes, upserts);
  - stamps it on creates;
  - **throws `TenantViolationError`** on any attempt to query, write or move rows to another org, including `{ in: [...] }` filters;
  - **throws `TenantContextMissingError`** if there's no tenant context at all (fail closed).
- **Shared catalogs** (`Game`, `Launcher`, `ShellApp`, `NotificationTemplate`, `Role`) may *read* platform rows where `organizationId IS NULL`, but can only write their own rows.

## Layer 3 — Database: Postgres Row-Level Security

`prisma/migrations/0002_rls` is generated by `scripts/gen-rls.mjs`:

- Every tenant table has `ENABLE` + `FORCE ROW LEVEL SECURITY` and a policy of the form `"organizationId" = app.current_org_id()`.
- `app.current_org_id()` = `NULLIF(current_setting('app.current_org', true), '')::uuid`. With no setting, every policy evaluates to NULL, so **zero rows** are returned.
- `withTenant()` runs `set_config('app.current_org', $org, true)` **inside the transaction**. The setting resets at commit or rollback, so it's safe with pooled connections. An integration test proves it doesn't leak to the next transaction.

### Database roles

| Login role | Member of | RLS | Used by |
|---|---|---|---|
| `arena_owner` | — (owner) | forced | migrations only |
| `arena_api` | `arena_app` | **enforced** | API, workers, edge sync |
| `arena_reporting` | `arena_readonly` | **enforced** | read replica / BI |
| `arena_platform_svc` | `arena_platform` | **BYPASSRLS** | Super Admin service only |

`BYPASSRLS` isn't inherited through role membership, so it is set on the platform login role itself. Runtime roles also lack privileges on:
- platform reference data;
- platform-managed tenant rows (`Subscription`, `OrganizationFeature`, `ImpersonationSession`, …);
- `UPDATE`/`DELETE` on ledgers.

## Super Admin access to tenant data

- **Aggregate platform views** (total orgs, online PCs, revenue) go through `arena_platform_svc`, in a separate service with its own auth (a `PlatformRoleAssignment` plus mandatory MFA).
- **Acting inside a tenant** requires an `ImpersonationSession`:
  - It needs a reason of at least 10 characters and an optional ticket reference, and it's time-boxed to 8 hours or less. The database enforces these limits.
  - Impersonated requests carry `impersonatorId` in the `TenantContext`. It's written on every `AuditLog` row and visible to the tenant.
  - `authorize()` refuses money-moving and privilege-granting actions during impersonation (`IMPERSONATION_BLOCKED`).

## Tests that guard isolation

| Test | What it proves | Needs DB |
|---|---|---|
| `tenancy.static.test.ts` | every model classified; every tenant table has RLS and a policy; composite FKs everywhere; ledgers have no `updatedAt` and are append-only; financial tables have idempotency keys | no |
| `tenant-scope.test.ts` | the Prisma layer injects, stamps and blocks cross-org access; the tenant context fails closed and is isolated across concurrent async flows | no |
| `rls.integration.test.ts` | as the real runtime role: A can't read, update, delete or insert into B; no context means zero rows; no leak across pooled transactions; ledgers can't be deleted | **yes** (CI) |
| `rbac.test.ts` | `WRONG_TENANT` is denied even for an org owner | no |

## Adding a new tenant table (checklist)

1. Add `organizationId String @db.Uuid`, `@@unique([id, organizationId])`, and composite relations.
2. `npm run codegen -w @arena/db`, which refreshes `TENANT_MODELS`.
3. Create the migration, then append `node scripts/gen-rls.mjs NewTable` output to it.
4. `npm test`. The static test fails if you forgot any of the above.
